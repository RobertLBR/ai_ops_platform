# 📘 AI 运维平台 — 产品使用手册

> 面向**使用者**（运维工程师、值班同学、技术管理者）的操作手册。
> 如果你要做部署/配置，请先看 [configuration.md](configuration.md)；本手册只讲「登录后怎么用」。

---

## 0. 三句话认识这个系统

1. **它是你的「老运维助手」**：把日志 + 指标 + 架构知识喂给大模型，自动给出**可追溯的根因分析**，而不是又一个要人盯的大屏。
2. **它只诊断、不修复**：全程只读，AI 给出的命令只展示、要你人工确认后自己执行。这是刻意的——安全边界比智能更重要。
3. **它越用越准**：你沉淀的故障经验（knownIssues）和反馈（准确/错误）会被下一次诊断复用。

## 1. 登录与鉴权

### 1.1 访问地址

系统默认监听 **3003** 端口（由 `config.yaml` 的 `server.port` 决定）。

- 直接访问：`http://<服务器IP>:3003`

### 1.2 两层鉴权（别混淆）

| 层级 | 由谁提供 | 说明 |
|---|---|---|
| **Web 登录（Basic Auth）** | nginx / 网关 | 访问页面前先弹账号密码。这是网络层访问闸门，与系统本身无关，由你的反代/网关配置决定。 |
| **API Token（Bearer）** | 本系统 | 页面调用后端接口时带的 `Authorization: Bearer <token>`。值来自 `config.yaml` 的 `server.apiToken`（或环境变量 `AIOPS_API_TOKEN`）。**仅存于浏览器 localStorage，不会上传。** |

> 若后端没配 `apiToken`，登录页面后右上角「API Token」留空即可；若配了，点右上角 **API Token** 按钮填入，可用「测试连接」校验有效性。接口返回 401 时会自动弹窗提醒。

### 1.3 顶栏速览

右上角常驻四个控件：

- 🟢/🔴 **后端在线 / 离线**：每 30 秒探活一次（离线说明后端没起来或端口不对）。
- 🔄 **实时监控开关**：见第 10 节。
- 🔑 **API Token**：设置/修改鉴权令牌。
- 🔗 **API**：新开标签打开 `/api/health`，便于快速自检。

## 3. 发起诊断（💬 发起诊断）

这是最常用的入口。三种触发方式的区别见下表，**手动提问**走的就是这个页面：

| 触发方式 | 入口 | 特点 |
|---|---|---|
| 手动提问 | 本页面 | 你描述问题 → 立即同步诊断，15~60 秒出结果 |
| 告警触发 | 告警流水（webhook） | 告警进来自动诊断，命中级别才推卡片 |
| 定时巡检 | 调度器（需在配置开启） | 周期性扫 error 日志，发现新异常才诊断 |

**填写字段：**

1. **问题描述 / 告警内容**（必填）：自然语言即可。例如：
   - `order-service 今早 9 点开始一直报 timeout`
   - 直接粘贴告警群里的告警文本，系统会自动识别服务名
   - `容器反复重启，怀疑 OOM`
2. **快捷模板**：点一下即把常用问题填进输入框（服务报错排查 / 接口超时 / 容器 OOM / 连接池耗尽 / 配置拉取失败 / 巡检）。
3. **服务（可选）**：下拉选择（来自服务注册表）。不选时系统会**从问题描述里自动识别**服务名；选了更准。
4. **取证时间窗**：
   - 快捷区间：近 15 / 30 / 60 / 180 / 360 分钟、近 24 小时。
   - 自定义：用时间选择器精确框定（支持「今天」「近 1 小时」等预设）。
   - 建议先用 **近 15~30 分钟**，不够再扩大。窗口越大取证越多、耗时越长。

**提交后：** 页面会显示分阶段进度（解析 → 拉取日志/指标 → 脱敏压缩 → 注入知识推理），通常 **15~60 秒**。完成后自动跳到诊断详情。

**常见失败原因（页面会提示）：**
① 大模型 API Key 未配或本机无法访问公网 API；② ES / Prometheus 不可达；③ 时间窗内无日志；④ 服务名不在注册表。可访问 `/api/datasources/health` 查看数据源可达性。

## 4. 读懂诊断结果（📋 诊断记录 → 详情）

诊断详情是系统**最重要**的页面。它的核心设计是**事实与推断在视觉上强制分离**——这是安全设计，不是排版偏好。

### 4.1 顶部信息条

| 字段 | 含义 |
|---|---|
| 状态 | 排队中 / 取证中 / 分析中 / 已完成 / 失败 |
| 级别 | info / warning / critical（仅成功产出结论时有） |
| 服务 / 触发方式 / 创建时间 / 取证窗口 / 诊断耗时 | 任务元数据 |
| 提问 / 告警内容 | 你输入或告警原文 |

### 4.2 结论四大区（按可信度分层）

- 🟢 **已确认事实**（绿框）：日志/指标中**可直接验证**的内容。可以信任。
- 🟠 **AI 推断**（橙框，标注「需人工确认后再行动」）：模型的推测。⚠️ **下手前必然先看到这是推断**，不要照着未确认的推断去重启服务。
- ⚪ **AI 声明的信息盲区**（灰）：诚实说明「查不到什么」。比编造结论更有价值。
- ✓ **建议检查项**（按优先级排序）：落地操作的 checklist。

### 4.3 根因候选

按可能性排序的 `#1 / #2 ...`，每条带 **置信度**（high / medium / low）。置信度低不代表错，代表证据链偏弱，需你结合经验判断。

### 4.4 只读诊断命令（🔒）

系统给出一串 **建议的只读命令**（如 `docker logs`、`df`、`journalctl`），并**永久标注「系统只读，不会自动执行」**。你确认后自行在目标主机执行。命令可一键复制。

> 为什么只给命令不给按钮执行？因为安全边界是代码级强制的：系统里**不存在「执行模型输出」的代码路径**。

### 4.5 证据区（可折叠展开）

- **日志模板**：原始上千行日志经脱敏+压缩后得到的几十个模板。表格含：级别、模板（变量已归一为 `<*>`）、出现次数、时间跨度、代表性样本。特殊标记：
  - 🟣 **全新模式**：基线期内从未出现过，最值得关注。
  - 🟠 **已知问题：xxx**：命中了你在注册表里沉淀的 `knownIssues`，直接关联 SOP。
  - 🟡 **基线 N 次**：与历史基线对比的频次。
- **监控指标**：诊断时从 Prometheus 拉取的 CPU/内存/磁盘/JVM 等指标。
- **成本与脱敏审计**：本次 prompt/completion token 数、所用模型、以及**脱敏审计**（只记命中类型与次数，绝不记原值）。

## 5. 诊断记录的筛选与状态

在 📋 诊断记录页：

- 顶部可按 **状态**（已完成 / 失败 / 分析中）和 **服务** 筛选。
- 列表每行显示：创建时间、服务、触发方式（手动提问/告警触发/定时巡检）、问题/结论、级别、状态、耗时、反馈、操作。
- 点任意行（或「详情」）进入详情页。

**任务状态流转：** `pending（排队中）→ collecting（取证中）→ analyzing（分析中）→ done（已完成）/ failed（失败）`。

**重启后中断的任务：** 后端启动时会自动回收「非终态」的历史任务，把它们标记为 `failed`，避免永远显示「分析中」。这在 `index.ts` 的 `db.markStaleTasksFailed()` 中处理——所以你看到的「分析中」任务若服务重启过，会变成「失败」，属正常。

## 6. 反馈与知识沉淀（最关键的长效动作）

每次诊断完，**请务必反馈**——这是系统「越用越准」的唯一来源，也是成果看板「有用率」的数据基础。

在详情页底部「你的反馈」区：

1. 选择 **准确 / 部分准确 / 错误**。
2. （可选）写补充说明。**若标记为「错误」，请务必写下真实根因**——这是知识库迭代最有价值的输入。
3. 点 **提交反馈**。
4. **沉淀为故障案例**：把这次诊断固化为可复用案例。下次同类日志命中时，系统会参考这些经验。

> ⚠️ 没有反馈，成果看板上的「结论有用率」永远是空的，对外汇报时就少了最核心的说服力。建议形成习惯：每次看诊断都顺手评一句。

## 7. 服务注册表（🗂️ 服务注册表）

这是诊断准确性的**地基**——AI 靠它把「物流那个服务」这种口语映射到真实 ES 索引、Prometheus 指标和部署主机。

### 7.1 数据源连通性看板

页面顶部实时探测 ES / Prometheus 是否可达，显示 `连通 N/M` 和每个源的「连通 / 不通 / 未知」。不通时请检查 `config.yaml` 里的 URL、网络与认证。

### 7.2 服务列表

表格含：服务（含别名 aliases）、等级（核心/重要/边缘）、技术栈、日志数据源（带连通性）、依赖关系、已知问题数。点行可展开看**部署信息**（主机/容器/端口/Jenkins Job/镜像仓库）和**已知问题清单**（匹配模式 + 原因 + 处置 SOP）。

- **aliases 越多**，服务名识别越准。
- **dependsOn / dependedBy** 帮助 AI 沿依赖链定位上游故障。
- **knownIssues** 是你沉淀的排障经验，会让 AI 优先命中已知问题而非从零推理。

### 7.3 AI 生成配置（🤖）

点 **AI 生成配置**（或某行「AI 重新生成」）可让 AI 根据日志样例自动生成服务注册表条目：

1. 粘贴一段日志样例 + 描述需求 → AI 生成结构化配置草案。
2. 系统做 **三层校验**（错误/警告），你可编辑调整。
3. 保存时**自动备份**旧 `config.yaml` 并**热生效**（无需重启）；手工改 `config.yaml` 则需重启后端。

每个服务的「生成记录」可点开抽屉查看**生成谱系**：时间、操作者、模型、校验结果、用户编辑 diff、AI 原始输出——全程可审计。

## 8. 告警流水与定时巡检（🚨 告警流水）

### 8.1 告警流水页

展示所有入站告警，含：触发时间、来源（Alertmanager/飞书/企微/手动）、级别、状态（告警中/已恢复）、服务、标题/描述。已关联诊断的会显示「查看」直接跳转；被降噪合并的标「已降噪」。

### 8.2 Webhook 接入（三种格式自动识别）

系统在 `config.yaml` 的 `alerts.webhook` 段配置，通过 HTTP POST 接收：

- **Alertmanager**：在 `webhook_configs` 填 `url: http://<host>:3003/api/webhook/alertmanager?secret=<secret>`，`send_resolved: true`。
- **飞书机器人**：`url` 改为 `/api/webhook/feishu`。
- **企微机器人**：`url` 改为 `/api/webhook/wecom`。

> 默认入口路径由 `alerts.webhook.path` 决定（默认 `/api/webhook/alertmanager`），飞书/企微为固定附加路径。

**降噪与自动诊断参数：**
- `dedupWindowSeconds`：同服务在窗口内的重复告警只记录、**不触发新诊断**（避免告警风暴）。
- `autoDiagnose`：是否自动触发 AI 诊断（默认 true）。
- `minSeverity`：最低触发级别（info/warning/critical），低于此级只记录不诊断。
- `secret`：可选共享密钥，请求需带 header `X-Webhook-Secret: <secret>` 或 URL 参数 `?secret=`。未配则不校验（仅限内网）。

### 8.3 定时巡检的节奏（重要，避免误解）

`alerts.scheduler.scanIntervalMinutes: 60` 控制的是**扫描轮次的触发间隔**，不是推送间隔。每一轮是：

```
一轮扫描 = 遍历所有非 edge 服务（串行）：
   免费前置闸（取证+脱敏+压缩，零 LLM 费用）
   → 无任何异常迹象（无新模板/无频率突增/无 ERROR/指标不 critical）就跳过
   → 否则 LLM 诊断，命中 warning/critical 或发现新模式才推一张卡片
```

所以你看到的「每隔几十秒推一张卡」，是**同一轮**里多个服务依次诊断完依次推送，不是每一轮只查一个服务。服务多 + 异常多时，一轮总时长 = 各异常服务 LLM 耗时之和，可能逼近甚至超过 60 分钟——此时防重入闸会跳过下一轮（日志记「上一轮扫描尚未结束，跳过本轮」），实际轮距被拉长。

**巡检推送卡规则：** 卡片标题**必须含「告警」**二字——飞书自定义机器人若开了「自定义关键词」校验，不含关键词会被拒收（错误码 19024）。

### 8.4 每日日报

调度器在 `dailyReportHour:dailyReportMinute`（默认 08:00）生成**结论式日报**（而非罗列数字），让大模型对当天度量做一句话总结，推送到 `reportWebhookUrl`（飞书群机器人）。日报同时触发过期诊断任务的清理（保留天数由 `storage.retentionDays` 决定）。

**手动触发日报（调试用）：** `POST /api/scheduler/run-daily-report`（需带 Bearer Token）。

**查看调度状态：** `GET /api/scheduler/status` 返回 `enabled / scanIntervalMinutes / 每日时间 / 上次扫描时间 / 是否正在运行 / 日报地址是否已配`。

## 9. 成果看板（📊 成果看板）

这是给**领导和自己**看价值的地方。三大核心指标：

| 指标 | 计算口径 |
|---|---|
| **累计节省人工（小时）** | 已完成诊断次数 × (人工基线 − AI 平均耗时)。人工基线取自 `metrics.manualBaselineMinutes`（默认 30 分钟，**请按真实排障经验填写**，否则数字无说服力）。 |
| **结论有用率（%）** | (完全准确 + 部分准确) / 有反馈的样本数。采用这个口径而非「完全准确率」，因为排障结论常能指出方向但细节需补充，部分准确同样产生价值。 |
| **告警降噪率（%）** | 降噪窗口内合并的告警数 / 总告警数。反映减少的无效打扰。 |

另含：诊断任务统计（累计/完成/失败/进行中、成功率）、成本与知识资产（累计 token、单次平均 token、沉淀案例数）、最近诊断列表。

> ⚠️ 汇报建议：① 这些数字的可信度取决于**从上线第一天就记录**；② 对外前请积累足够样本（建议 ≥ 30 次诊断且有反馈），小样本百分比易失真；③ 主动说明「全程只读、不做自动修复」——这是风险可控的证据，不是能力不足。

## 10. 实时监控开关（🔄，右上角）

一键开启 **5 秒级**告警/诊断状态自动刷新，适合值班盯屏。要点：

- **默认 OFF**，开关状态存浏览器 localStorage，多个标签页通过 BroadcastChannel 同步。
- **多 Tab 领导者选举**：只有「leader」标签页真正发请求，N 个标签页不会产生 N 倍轮询（关掉 leader 标签页，继任者自动接管）。
- **零 AI 费用**：监控只轮询只读状态快照，**不调用大模型**。
- 请求失败会指数退避（5→10→20→40→60 秒封顶），成功后复位。

> 日常使用保持 OFF 即可；只有需要「实时看诊断进度/告警变化」时才开。

## 11. 审计日志（🔐 审计日志）

系统全程只读的客观证据，向甲方/领导汇报「风险可控」时可直接引用。动作类型图例：

| 动作 | 含义 |
|---|---|
| 发起诊断 | 创建任务，开始只读取证 |
| 诊断完成 | 成功产出结论，记录耗时/模板数/token/脱敏命中 |
| 诊断失败 | 执行失败（数据源不可达/无日志等），记录原因 |
| 人工反馈 | 标记准确/部分准确/错误，迭代知识库与统计有用率 |
| LLM 调用 | 只记 token 数与送入字符数，**绝不记 prompt 内容**（已脱敏佐证） |
| 日报推送 | 调度器推送每日运维报告 |

执行者分 `system` / `scheduler` / `user` 三类。

## 12. 常见问题 FAQ

**Q1：诊断很慢/转圈好久？**
正常。AI 推理（尤其长上下文）通常 15~60 秒，少数复杂场景更久。页面有分阶段进度提示。若长时间无响应，检查大模型 API 是否可达（`/api/health`、确认本机能访问公网 API）。

**Q2：为什么 `/favicon.ico` 返回 500？**
旧版本 bug：SPA 兜底路由用相对路径调用 `sendFile` 会抛错。已修复（`resolveWebRoot` 强制绝对路径）。若仍出现，是服务跑了旧镜像，请 `git pull && docker compose up -d --build` 升级。也可在 nginx 加 `location = /favicon.ico { access_log off; return 204; }` 临时止血（但客户端路由刷新 500 仍需升级解决）。

**Q3：推送了告警卡片但群里没看到？**
飞书自定义机器人若开了「自定义关键词」，消息必须含关键词（本系统巡检/日报标题含「告警」）。错误码 19024 = 关键词不匹配。检查机器人配置或企业群关键词设置。

**Q4：服务名识别不出来/诊断跑偏？**
服务注册表的 `aliases` 不全或 `datasourceId` / `indexPatterns` 配错。去 🗂️ 服务注册表补全别名、核对数据源连通性。

**Q5：数据源显示「不通」？**
检查 `config.yaml` 里对应 ES/Prometheus 的 URL、网络可达性、账号密码（建议只读账号）。页面顶部连通性看板实时反映后端能否访问。

**Q6：后端离线（顶栏红点）？**
后端进程没起来或端口不对。检查：`docker compose ps`、`docker compose logs -f ai-ops`、确认 `server.port` 与你的访问端口一致（默认 3003）。

**Q7：定时巡检为什么没按 60 分钟跑一次？**
见 8.3 节——`scanIntervalMinutes` 是轮次间隔，一轮内串行诊断多个服务。且需 `alerts.scheduler.enabled: true` 才生效（默认 false）。

**Q8：怎么确认系统真的没改过生产？**
看 🔐 审计日志：所有动作都是诊断/反馈/日报，**没有任何写操作**；AI 建议命令只展示不执行（`security.readonly` 白名单 + 危险模式黑名单 + shell 元字符拦截三重校验）。可用 `POST /api/security/check-command` 自测任意命令是否被拦截。
